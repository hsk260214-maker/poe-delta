# FEAT-010 거래소 검색 결과 개수 설정과 이어 불러오기

상태: 기획안 v3, 기획 리뷰 3/3 대상(2/3 보완: 요약 계산 시점, 링크 기준, 끝 안내 문구). 출처: `docs/BACKLOG.md` 6번 (2026-11-20 머성 요청).

## 1. 범위

- 앱 안의 결과 표를 쓰는 **게임 위 시세 모드(API)** 만 대상. 브라우저 모드와 검색 조건 payload는 바꾸지 않는다.

## 2. 현재 동작 (코드 근거)

- `app/trade/trade_window.py` `search()`: 검색 응답 ID 중 `[:20]`을 10개씩 두 번 조회한다. 나머지 ID는 버린다.
- `app/trade/query.py` `result_rows()`: 응답을 행으로 바꿀 때 다시 `[:20]`으로 자른다. `summary()`는 앞 10행으로 가격 요약을 만든다.
- `app/trade/api.py` `fetch()`: 한 번에 최대 10개 ID. 요청 제한은 기존 `RateLimiter`가 처리한다.
- 외부 자료(공식 문서 아님): 검색 한 번에 받는 ID는 최대 100개로 관측된다.

## 3. 설정

- `거래소 설정`에 `처음 불러올 매물 수`: 10~100, 10 단위, 기본 20(지금과 같음). 키 `result_count`, 즉시 저장. API 모드가 아니면 다른 API 전용 설정처럼 비활성화.
- 저장값이 숫자가 아니거나 범위 밖·10 단위가 아니면 20을 쓴다.
- 값은 검색을 시작할 때 읽어 그 검색에 고정한다(검색 중 설정을 바꿔도 다음 검색부터 적용).

## 4. 검색 세션

검색 한 번을 **세션**으로 묶는다. 세션은 다음을 따로 가진다.

- `ids`: 검색 응답의 ID 목록(받은 그대로), `total`: 응답의 전체 매물 수, 검색 ID와 결과 링크.
- `next`: 다음에 조회할 ID 위치(처리 완료 위치). `rows`: 실제 표에 붙인 행.
- 요청 중 여부. 한 세션에서 요청은 한 번에 하나만 진행한다. 처음 조회와 추가 조회는 겹치지 않는다.

### 4.1 조회 규칙 (처음·추가 공통)

- 한 번에 `ids[next:next+10]` 한 배치만 조회한다(기존 `fetch` 10개 제한 그대로).
- 행 변환은 배치마다 따로 한다. 그래서 `result_rows()`의 `[:20]` 제한에 걸리지 않는다. `result_rows()`는 바꾸지 않는다.
- 배치 응답의 매물은 **검색 ID 순서**로 정렬해 붙인다. 응답에 빠진 ID는 건너뛰고 처리 완료로 본다.
- 배치가 성공하면 `next`를 배치 끝으로 옮긴다. 실패하면 `next`와 이미 붙인 행은 그대로 두고 오류·대기 문구만 보여 준다. 다음 하단 입력이 같은 배치를 다시 요청한다.
- 처음 조회: `처음 불러올 매물 수`에 이를 때까지 배치를 차례로 조회한다. 중간 배치가 실패하면 앞선 성공 행을 유지하고, `next`는 실패한 배치 시작에 둔다. 검색 자체가 성공했으므로 결과 링크는 열 수 있다.
- 결과 요약(`summary`): 처음 조회가 정상으로 끝나거나 중간 배치 실패로 멈춘 시점까지 확보한 **처음 조회 행 전체**로 기존 `summary()`를 한 번 계산하고, 그 뒤 추가 조회로는 바꾸지 않는다. 기본 20일 때는 v1.2.6과 같은 행 집합이라 요약도 같다.
- `거래소에서 열기` 링크: 검색 요청 자체가 성공해 검색 ID가 있으면 사용할 수 있다. 첫 조회 배치가 실패하거나 빈 응답이어도 링크는 쓸 수 있다.
- 상태 줄에 `표시 M / 받은 N개`를 덧붙인다(M = 붙인 행 수, N = `len(ids)`).

### 4.2 이어 불러오기 입력

- 사용자의 **명시적 하단 입력**만 추가 조회를 시작한다.
  - 결과 표가 맨 아래일 때(스크롤이 없는 경우 포함) 아래로 휠.
  - 스크롤바를 사용자가 직접 끌거나 눌러 맨 아래에 닿았을 때.
  - 마지막 행에서 `↓`·`Page Down`·`End`.
- 행을 붙이거나 표 크기가 바뀌어 스크롤 위치가 맨 아래가 되는 것만으로는 요청하지 않는다(연쇄 요청 없음).
- 요청 중이거나 요청 제한 대기 중이면 추가 입력은 요청하지 않고 대기 문구만 유지한다. 대기가 끝난 뒤 다시 하단 입력을 하면 같은 배치를 요청한다. 자동 재검색은 하지 않는다.

### 4.3 끝 안내

- `next == len(ids)`이면 더 요청하지 않는다. 안내는 표시 행 수가 아니라 **조회한 ID** 기준이며, 상태 줄의 `표시 M / 받은 N개`와 함께 보인다(누락이 있으면 M < N).
  - `len(ids) == 100`이고 `total > 100`: "받은 100개 매물 ID를 모두 조회했습니다. 더 보려면 조건을 좁혀 다시 검색하세요."
  - 그 밖에 `total > len(ids)`: "받은 매물 ID를 모두 조회했습니다."
  - `total <= len(ids)`: 안내 없음.

### 4.4 세션 무효화

- 다음 경우 세션을 끝내고, 늦게 도착한 완료·실패는 아무 것도 바꾸지 않는다(행, 요청 중 상태, 대기 문구, 링크, 버튼, 리그 목록 모두).
  - 다시 검색, 다른 아이템 불러오기, 검색 조건·리그 편집, 서버·모드 변경, 창 닫힘.
- 기존 `_generation` 방식을 세션 단위로 쓴다.

## 5. 범위 밖

- 받은 ID를 넘는 매물을 위한 자동 재검색, 정렬 변경, 브라우저 모드.

## 6. 완료 기준 (모의 거래소 클라이언트로 오프라인 검증)

1. 설정 30: 처음 조회 3배치, 30행이 검색 ID 순서로 렌더링된다. 기본 20은 v1.2.6과 같은 표·요약·링크.
   - 첫 배치에서 매물 일부가 빠지거나 가격이 비고 두 번째 배치가 요약에 필요한 행을 채우는 경우, 요약이 v1.2.6과 같다.
   - 추가 조회 뒤에도 요약은 바뀌지 않는다.
   - 검색은 성공하고 첫 조회 배치가 실패·빈 응답이어도 링크를 쓸 수 있다.
2. 잘못된 설정값은 20으로 처리되고, 검색 중 설정 변경은 다음 검색부터 적용된다.
3. 하단 입력(휠·스크롤바·키) 한 번에 다음 배치 한 번만 요청해 아래에 붙인다. 붙이기·레이아웃 변경으로는 요청이 생기지 않는다. 요청 중 반복 입력도 요청을 늘리지 않는다.
4. 부분 응답(일부 ID 누락)과 빈 응답은 처리 완료로 넘어가고, 순서가 섞인 응답은 검색 ID 순으로 붙는다.
5. 실패(처음 조회 중간 배치 포함): 앞선 행 유지, 같은 배치를 다음 하단 입력에서 다시 요청.
6. 요청 제한: 대기 중 입력은 요청하지 않고, 대기 후 입력에서 같은 배치를 요청한다.
7. 끝 안내: 100개 ID를 다 조회하고 전체가 더 많을 때만 100개 ID 문구, 더 적게 받았으면 "받은 매물 ID를 모두 조회" 문구. 100개 ID 중 일부가 응답에서 빠진 경우 `표시 M / 받은 100개`(M < 100)와 100개 ID 문구가 함께 보인다.
8. 무효화: 다시 검색·다른 아이템·조건/리그 편집·서버/모드 변경·닫힘 뒤에 도착한 이전 세션의 성공·실패가 화면 상태를 바꾸지 않는다.
9. 브라우저 모드와 검색 조건 payload는 바뀌지 않는다.
