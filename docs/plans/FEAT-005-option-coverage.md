# FEAT-005 장비 미지원 옵션 55종류 · 바알 사원 지도 검색

상태: 기획안 v3(2/3 승인 후 개정), 기획 리뷰 3/3 대상. 개정 내용은 §5.2 포함 판정 1줄과 §5.4. 기준: 공개 v1.1.9(커밋 `129bedd`), Awakened PoE Trade(APT) 고정 커밋 `803d188d1359c4d5b1e3826da5dc680ea74a158f`(3.30 최신본 `57b313c`와 거래소 데이터 동일 확인).

## 1. 목적과 원칙

- 회색(검색 불가)으로 남은 장비 옵션을 검색할 수 있게 하고, 등급 표시 없는 `바알 사원 지도`가 막히는 문제를 해결한다.
- 넓은 대체 검색 금지. 근거가 없거나 모호하면 사유와 함께 회색으로 남기고 payload에서 뺀다. 토글만으로 요청하지 않는다. 두 검색 모드는 같은 쿼리를 쓴다.
- RePoE 감사는 후보 발굴용이다. 출시 근거는 실제 `Ctrl+C` 원문과, 앱이 만든 그대로의 카카오 브라우저 링크다. 브라우저 결과가 0건이거나 일부 갈래만 나오면 나머지 갈래의 검증으로 보지 않는다.
- 이 문서는 실제 거래소 확인 허가가 아니다. 카카오 링크 확인은 아래 게이트에 적은 개수만, 머성이 직접 연다.

## 2. 현황 근거

- 감사: `data/mods_ko.json` 24개 장비 부위 3,899개 형태 → v1.1.9 기준 미지원 55종류(묶음 27, 후보 여러 개 9, 문구 연결 실패 19). scratch `equipment-remaining-diagnosis.txt`.
- APT 재현: 고정 커밋 소스(`renderer/src`)와 `en/stats.ndjson`으로 A·B 36종류의 APT 해석 결과를 오프라인 재현했다. scratch `apt-resolution-AB.txt`. 색인 재현은 `renderer/src/assets/make-index-files.mjs`와 같은 방식(매처마다 `advanced` 또는 `string`의 FNV-1a 32비트 해시, 해시 순 안정 정렬, 같은 이진 탐색)이며 해시는 `@sindresorhus/fnv1a` ^3.0.0의 UTF-8 FNV-1a로 가정했다. 36종류 모두 문구별로 줄 하나에만 걸려 해시 가정이 결과에 영향을 주지 않았다.
- 감사 문구 한계: RePoE 한국어가 3.30 게임 문구와 다를 수 있다. 예: 감사 `주변에 희귀 또는 고유 적이 있는 경우 공격 속도 #% 증가` ↔ APT 한국어 `6미터 내에 희귀 또는 고유 적이 있는 경우 공격 속도 #% 증가`.

## 3. APT가 실제로 하는 일 (고정 커밋 코드 근거)

1. **문구 맞추기** — `parser/stat-translations.ts` `_statPlaceholderGenerator`(L80~134), `tryParseTranslation`(L136~): 줄의 숫자를 찾아, 정해진 순서로 일부 숫자는 그대로 두고 나머지만 `#`로 바꾼 문구를 차례로 만든다(숫자 1개: 그대로 → `#`, 숫자 2개: 둘 다 그대로 → 첫째만 → 둘째만 → 모두 `#`, 3~4개는 `PLACEHOLDER_MAP`). 매처 `string`/`advanced`와 **정확히 같은** 첫 문구를 쓰고, 그 항목에 해당 종류(explicit·crafted 등) ID가 없으면 다음 문구로 넘어간다. `#`로 바뀐 숫자만 값이 된다(고정 숫자 `6미터`, `4초`, `15당`은 값이 아니다).
2. **묶음 해석** — `_resolveTranslation`(L263~319): 그 종류 ID를 가진 항목이 하나뿐이면 그것만 쓴다(전략과 무관). 아니면 `trivial-merge`는 맞춘 문구를 가진 항목들의 ID를 합치고, `percent-merge`는 퍼센트 항목의 매처 고정값이 100일 때만 다른 항목 ID를 접두어 `{empty_if_100}`(다른 항목이 `#` 없는 단일 매처) 또는 `{div_by_100}`로 붙여 합친다. 100이 아니면 문구가 맞는 항목 하나만 쓴다.
3. **전송** — `web/price-check/trade/pathofexile-trade.ts` `appendAndFilter`·`everyTradeIdToQuery`·`tradeIdToQuery`(L894~935): ID가 하나면 기본 `and` 묶음에 넣고, 여럿이면 **그 옵션 하나마다** `{"type":"count","value":{"min":1},"filters":[...]}` 묶음을 따로 만든다. 묶음 안의 모든 ID에 같은 최소·최대를 넣고, `{div_by_100}`은 최소·최대를 100으로 나누고, `{empty_if_100}`은 값이 100이면 값을 비운다. 옵션 행 두 개를 켜면 `count` 묶음이 두 개 생겨 둘 다 만족해야 한다(그룹끼리는 AND).

## 4. A·B 36종류 결과와 개방 범위

| 규칙(검색 의미) | 대상(종류) | APT 결과 | 개방 |
|---|---|---|---|
| R1 단일 ID | 처치 시 생명력·에너지 보호막 회복, 원소·물리·카오스 피해 생명력 흡수 5종, 원소 약화 저주, 물리 피해 감소 무시, 제작 시전 속성 부여 불가·최근 피격 없을 때 이동 속도·치명타 시 격분 충전 | ID 하나, 일반 `and` 필터 | 기존 지원 옵션과 같은 형태라 오프라인 회귀로 개방. 카카오 확인 불필요 |
| R2 같은 종류 ID 여러 개 `count` | 공격·주문 피해 막기(일반·제작, `+#%`·`#%의 확률로 막아냄`), 인내 충전당 공격 막기, 처치 시 마나 회복, 경험치 | `count` 최소 1, 같은 종류 stat ID 2개, 같은 최소·최대 | 대표 1개(일반 `공격 피해 막기 확률`) 카카오 확인 후 R2 전체 개방 |
| R3 `count` + 다른 형식 ID | 모든 망령 소환 젬 레벨(`stat` + `indexable_skill`) | `count` 최소 1, 형식이 다른 ID 2개 | 근거가 R2와 달라 회색 유지(별도 허가 시 대표 1개) |
| R4 `percent-merge` 100 + `{empty_if_100}` | 명중 시 인화성·취약성 저주 | `count` [저주 확률 ID 최소 100, 저주 효과 ID 값 없음] | 대표 1개(인화성) 카카오 확인 후 R4 개방 |
| R5 `percent-merge` 100 + `{div_by_100}` | 치명타 시 플라스크 충전 | `count` [확률 ID 최소 100, 충전 ID 최소 1] | 1슬롯뿐이라 회색 유지(별도 허가 시 대표 1개) |
| B 고정 숫자로 단일 결정 | 힘·지능·민첩 15당 피해, 지능·힘 16당 주문 피해, 정확도 200당 투사체 공격 피해, 정지 상태일 때 4초마다 인내 충전 | ID 하나(예: `15당`은 `#% increased Damage per 15 Strength` 항목, `4초마다`는 문구 그대로 맞는 항목) | §5 매칭 계약 적용 시 R1과 같은 형태 → 오프라인 회귀로 개방 |
| B → R2 | 처치 시 #%의 확률로 4초 동안 맹공 획득(일반·제작) | 일반: `4초` 문구로 맞춘 `trivial-merge` ID 2개 `count` / 제작: ID 하나 | 일반은 R2 게이트를 따른다. 제작은 R1 |

- "후보가 여러 개" 9종은 진짜 중복이 아니었다. 현재 앱의 `skeleton()`이 모든 숫자를 `#`로 바꿔 `15당`과 `100당`, `4초`와 `10초` 같은 서로 다른 옵션을 합쳐 버린 것이 원인이다. 문구 기반 OR 묶음은 쓰지 않는다.
- 최소값: 각 행의 기본 최소값은 지금 규칙(복사 값의 90%, 고정값 매처는 그 값)을 `#` 값에만 적용한다. R4·R5에서 100은 고정값이다.

## 5. 매칭 계약 (C 포함, 전체 옵션에 적용)

### 5.1 두 경로

- **K(한국어 직접)**: APT 고정 커밋 `ko/stats.ndjson`의 한국어 매처 원문으로 §3의 1·2를 그대로 수행.
- **E(번역)**: 기존 한→영 번역 결과에 `en/stats.ndjson` 원문으로 §3의 1·2를 수행. 현재 `skeleton()` 비교는 이 APT식 비교로 바꾼다.
- 각 경로의 결과는 셋 중 하나: **확정**(종류 ID가 있고 묶음 해석이 끝남), **미매칭**(맞는 문구 없음 또는 번역 없음), **모호**(`select`인데 부위로 결정 안 됨, 해석 불가 전략, 같은 문구가 서로 다른 의미 줄에 걸림 등).

### 5.2 판정표

| K | E | 결과 |
|---|---|---|
| 확정 | 확정, 같은 검색 의미 | 사용 |
| 확정 | 확정, 다른 검색 의미 | **회색**: "한국어·번역 연결 불일치", payload 제외 |
| 확정, 여러 ID(한국어 문구 겹침) | 확정, 단일 ID이며 K의 ID 집합에 포함 | **E 단일 사용** (§5.4) |
| 확정 | 미매칭 | K 사용 |
| 미매칭 | 확정 | E 사용(현행) |
| 모호 | 무엇이든 | 회색(모호를 미매칭으로 보고 우회하지 않음) |
| 무엇이든 | 모호 | 회색 |
| 미매칭 | 미매칭 | 회색(현행 사유) |

- **같은 검색 의미**: 정규화한 뒤 다음이 모두 같아야 한다 — 종류(explicit·crafted 등), 전송 형태(단일·`count`), ID 집합과 접두어(`{empty_if_100}`·`{div_by_100}`), 부호(`inverted`·`negate`), 고정값, 값이 되는 숫자의 개수와 위치. 같은 `ref`라도 위 항목이 다르면 다른 의미다.
- K로 확정된 행의 기본 최소값은 K가 정한 `#` 값으로 계산한다(문장 고정 숫자를 집지 않는다). 번역이 없어도 기본값이 생겨야 한다.
- APT에 없는 종류 ID는 다른 종류로 대체하지 않는다(예: 제작 ID가 없으면 explicit로 바꾸지 않고 회색).
- 젬 이름표에 없는 보조 젬·스킬 이름은 K 경로로 먼저 해결하고, 대응표는 실제 원문으로 확인된 것만 추가한다.

### 5.3 기존 지원 옵션 회귀

- 감사 전체(3,899개 형태)와 저장된 원문 고정 자료 전부를 바뀌기 전/후로 비교해 셋으로 나눠 보고한다: (a) 결과 payload가 바이트 단위로 같음 — 대부분이어야 한다, (b) 새로 검색 가능, (c) 이전에 검색되던 행이 달라지거나 회색이 됨 — 항목마다 사유(의도한 불일치 차단인지)를 적고 리뷰가 승인한 것만 허용한다.

### 5.4 개정 근거 (v2 구현의 v1.1.9 대비 비교)

- v2 구현을 v1.1.9와 같은 감사·원문으로 비교하니 새로 검색되는 줄 79개, **막히는 줄 230개**였다. 막힌 줄은 목걸이·반지·허리띠·장갑 등 9~11개 부위의 화염·냉기·번개 저항(223줄)과 오라 스킬 부여 7줄이다.
- 저항: APT 한국어 데이터에서 `화염 저항 +#%`가 다른 옵션 `Fire Resistance is #%`(`explicit.stat_763311546`)와 한글 표기가 겹쳐 K가 두 ID를 묶는다. E는 기존에 쓰던 `+#% to Fire Resistance`(`explicit.stat_3372524247`) 하나로, K 집합의 한 원소다. 영문 문구가 겹침을 구분한 결과이므로 E 단일을 쓴다. 223줄 모두 이 경우이며 payload는 v1.1.9와 바이트 단위로 같다.
- 반대 방향(K 단일이 E 묶음에 포함, 예: 일반 공격 피해 막기)은 이번 개정에 넣지 않는다. 지금처럼 회색이다.
- 오라 스킬 부여: v1.1.9의 스킬 부여 변환이 `Skill`을 떼어 `Grants Level # ​Anger`(고유 아이템용 `explicit.effect_2014162730`)로 연결하는 결함이 있었다. 장비 옵션의 정답은 `Grants Level # Anger Skill`(`explicit.stat_449494711`)이며 K도 이것을 고른다. 번역을 `Grants Level N X Skill`로 먼저 맞추고, 없을 때만 기존 `​X` 형식으로 맞추게 고치면 7줄 모두 K와 E가 일치한다. 이 7줄은 v1.1.9 대비 의도한 수정(c)이다.
- 개정 후 기대: 막히는 줄 230 → 0. (c)에는 오라 스킬 7줄 ID 교정과 기존 승인 항목만 남는다.

## 6. 바알 사원 지도 (D, 1/3 승인 방향)

- 정확 베이스(현지화 이름) + 현행 희귀도(`nonunique`)·역병 아님·타락 동작 유지, `map_tier` 없음, 몬스터 레벨 선택, 고정 옵션 `지역에 방어되는 바알 그릇 10개 추가 등장`은 기본 해제.
- `TIERLESS_MAP_BASES`와 지도 정체성 검사를 전역으로 완화하지 않는다. 이 베이스만 추가하고, 카카오 링크 확인 전에는 이 베이스만 닫아 둔다.
- 게이트: 앱이 만든 그대로의 카카오 링크 1개에서 바알 사원 지도(타락)만 나오는지 머성이 확인. 0건·미확인이면 열지 않는다. 공식 서버 이름·payload는 오프라인 회귀로만 확인하며 공식 거래소 검증으로 표현하지 않는다.
- 고정 자료: 머성 원문(`고립된 연결부` 희귀 바알 사원 지도, 타락).

## 7. 요청 예산 (머성이 여는 카카오 링크)

- 기본 3개: 바알 사원 지도 1, R2 막기 1, R4 인화성 저주 1. R3·R5는 머성이 따로 허가할 때만 각 1개.
- 대표 원문 요청(문구 연결 확인용, 요청 아님): 희귀도, 6미터 내 희귀·고유 적, 명중 시 실명, 주변의 적 저항 감소, 제작 주문 발동 옵션 각 1개.

## 8. 범위 밖

- 다른 수호자 지도, 살덩이 일반 단계·단계 없는 고유 살덩이, 장비가 아닌 품목. 앱의 실제 거래소 API 요청 검증.

## 9. 완료 기준

1. 바알 사원 지도 원문이 검색되고 쿼리에 `map_tier`가 없다. 게이트 전에는 이 베이스만 막혀 있다.
2. R1·B 단일 결정 행은 APT 재현 결과와 같은 ID로 일반 `and` 필터가 된다.
3. R2·R4는 옵션 하나마다 `count`(최소 1) 묶음이 되고, 같은 최소·최대(접두어 규칙 포함)가 들어간다. 행 두 개를 켜면 묶음 두 개가 생긴다. 게이트 전·R3·R5는 회색이다.
4. 판정표의 모든 칸이 테스트로 고정된다(특히 확정+확정 불일치, 모호 우회 금지, K 확정 시 기본 최소값이 `#` 값에서 나옴).
5. 대표 원문은 연결되거나, 모호하면 사유와 함께 회색이다(전부 활성화가 아님).
6. §5.3 회귀 보고에서 (c) 항목은 모두 사유가 있고 승인됐다. 기존 원문 회귀 테스트가 모두 통과한다.
